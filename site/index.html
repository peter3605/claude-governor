Six sessions. One laptop. Everything crawls.

Each session fans out into subagents and builds with no idea the others exist. Twelve things compile at once on eight cores, the fans spin up, and every session gets slower — including the one you are watching.

Build Governor is a jobserver for Claude Code. One small daemon holds a single budget for the whole machine. Every session asks before it starts an expensive build, and gets told a number instead of guessing one.

§1  //  The problem

A session cannot see
the other sessions

Claude Code is good at parallelism. It will launch a test suite, a build, and four subagents because all of those are reasonable things to do.

What it cannot know is that three other sessions on the same laptop just did the same. Nothing in the stack arbitrates this — each session is a separate process tree making locally sensible decisions, and the machine absorbs the sum of them.

On a desktop with headroom you never notice. On a laptop you notice immediately, and the symptom is the worst kind: everything gets slower, so there is nothing to blame.

The oversubscribed machine also delivers less work. Ten builds thrashing on eight cores spend their time on context switches and memory pressure, not compiling. You pay the heat and the fan noise and get fewer finished builds for it.

§2  //  What it actually does

The same fan-out.
Run twice.
Measured from outside.

Ten builds launched at once — once with no hooks at all, once against a live daemon. Every number below came from an independent watcher rather than the governor's own logs, because a control loop reporting on its own behaviour proves nothing.

The first attempt was thrown away. The governed arm stopped early after its first few refusals, which left the two arms with unequal session lifetimes and made the comparison worthless. It was re-run with the refusals declared up front, and the discarded run is in the record.

§3  //  How it works

A gate, a daemon,
and a budget that moves

        claude code session
               │
          PreToolUse hook
               │
          ┌────────▼────────┐
          │  classify       │  ~5 µs, no I/O
          └───┬─────────┬───┘
     cheap │         │ build-shaped
          ▼         ▼
     pass through   unix socket
     never dials         │
                        ▼
          ┌──────────────────────┐
          │  daemon              │
          │   lease table        │
          │   AIMD loop          │
          │   max-min fair queue │
          └───┬──────────────┬───┘
              │              │
        GRANT            WAIT ≤ 20s
        lease held       then refuse

  any failure, anywhere ──▶ FAIL OPEN

FIG.03 — the admission path. Only 18.4% of Bash calls reach the socket; they carry 78.6% of the child CPU.

The gate classifies before it does anything else

A pure function reads the command text in about 5 microseconds and decides whether it is build-shaped. git status and cat never touch the socket at all.

One lease table for the whole machine

Started lazily by the first gate that needs it. Leases are divided max-min fair across sessions, the rest queue FIFO, and a dead process has its lease reaped by TTL and PID liveness.

The budget is a control loop, not a constant

Additive increase while the machine has room and something is waiting; multiplicative decrease the moment the queue goes deep. Climbs one slot per second, halves on the way down — the asymmetry TCP uses, for the same reason.

It controls on run-queue depth, not CPU

A build machine at 100% CPU with a shallow queue is working, not in trouble, and utilisation saturates at 1.0 exactly where the useful distinctions begin. Measured: the CPU climb condition held on 0 of 471 saturated ticks.

Thermal is a backstop, honestly labelled

A serious reading floors the budget. On a fanless Mac over 101 hours that never once fired, so it is documented as carried for hardware that throttles rather than claimed as load-bearing. No sudo.

§4  //  The unit

One slot
is 1.2 cores

Not one agent. Not one session. A slot is the measured p90 peak child cores of an ordinary compile, so the common case weighs exactly 1 and 3/6 slots reads as "about three ordinary builds' worth of load."

The subagent figure is a population-level marginal, not a per-agent cost: the sampler is host-wide and the measured machine never ran fewer than three concurrent sessions. The distinction is kept everywhere it appears.

Which is how the project changed its own mind

It began as a subagent limiter. A week of tracing said agents cost about 0.098 cores each, near-constant, with a negative maximum marginal — the busiest seconds on the machine had no agent live at all.

The CPU was going to the builds the agents launched. So the controlled variable moved to build concurrency, and agents kept a weighted lease rather than a count. A budget that counted a subagent and a heavy build alike would govern neither.

§5  //  What you see

A refusal that
tells you why

A governor that silently changes behaviour is untrustworthy. The number is in your status line, and every refusal names the figures behind it.

$ governor status
budget 6
in use 3
slots held 3
agents 0
waiting 0
cpu 0.78
thermal nominal
session 16c20e52-7a3f-4b1e-9d02-5e8c41a7b3f9 weight 1 tentative 0 confirmed 1
session 9b04a7e1-c6d5-4f80-a1b3-2e7f90d4c815 weight 1 tentative 0 confirmed 2
──── status line ────────────────────────────────────
3/6 slots (1 yours) - cpu 78% - thermal ok
──── a refusal, in session ───────────────────────────
Not enough free build slots (3/6 build slots held, this one needs 4, CPU 78%, thermal: nominal). This command was not run. This is a large build and the slots left free are not enough for it. Wait a few seconds and run exactly the same command again; do not look for a different way to build, and do not treat this as a build failure.

Verbatim: each line is what the shipped binary prints for that state. A refusal names the number, the cause, and one concrete instruction — a vague one produces a retry loop that burns tokens. A refused build is told to wait and run the same command again, never to "do it inline": nothing else on the machine can compile that package, so inline advice it cannot act on would send it looking for a worse way to build. The gate prefers to wait rather than refuse wherever the wait fits inside the hook timeout, because a stall costs nothing and the model never has to reason about it.

  • Overrides, when you disagree. limit pins the budget, pause stops gating without stopping the daemon, boost doubles one session's share, resume releases either.
  • An MCP tool, so a session can ask first. governor__request_build checks for room before committing to something expensive, instead of discovering the answer by being refused.
  • A doctor that diagnoses rather than describes. governor doctor checks the install, daemon, socket, hooks, and whether any running session predates the install — and names the fix for each thing it finds.
§6  //  The two guarantees

What this asks of you
is a hook on
every build

That is an intrusive thing to install, so these come before any feature.

  • No sudo, ever. Nothing runs as root and nothing asks.
  • No telemetry. Nothing collected, nothing sent.
  • One static binary. No runtime, no background updater.
  • It never kills anything already running. Admission control only.

It fails open

Daemon down, socket unreachable, reply slow, wrong protocol version, garbled payload — the build goes ahead ungoverned. A broken governor can never stall a session. Every hook has a hard deadline inside Claude Code's own, and the fail-open test drives the gate through each failure shape it knows and requires every one to let the work through.

It comes out clean

governor uninstall removes the plugin, stops the daemon, and restores settings.json byte for byte. A test installs into a scratch home, uninstalls, and fails on any difference in a digest of the whole directory — on every push against clean Debian and Alpine, and on every release against a clean macOS machine using the published download.

§7  //  Install

Three routes,
one destination

They all end in the same place: one plugin at ~/.claude/skills/build-governor/ and one governor binary. The marketplace entry carries no second copy — it points Claude Code at the tree the binary already wrote, so both registrations load the same files and cannot double up.

01 — The one-liner

$ curl -fsSL https://raw.githubusercontent.com/peter3605/claude-governor/main/install.sh | sh

02 — Homebrew

$ brew install peter3605/claude-governor/governor && governor install

03 — Claude Code marketplace

$ claude plugin marketplace add peter3605/claude-governor $ claude plugin install build-governor@claude-governor

Once the binary is installed by either route above.

It measures your machine first

Install ends by running governor calibrate: your core count, your performance-core split, your RAM, and what your run queue already sits at while you work — then a short, announced load probe of 3.75 seconds to find how many cores your hardware really delivers in parallel.

That is not the number it advertises: a laptop with four performance and four efficiency cores measures about 5.6 of 8.

⚠ Sessions you already have open stay ungoverned

Claude Code binds hooks when a session starts, so an install cannot reach into a session that is already running. Those stay ungoverned for the rest of their lives.

Install counts them and names them, governor doctor fails while any of them is still running, and the status line reads governor: ungoverned - restart to enable rather than a misleading slot count. Restart them and it takes effect.

§8  //  What this is, and is not

Honest about
the edges

  • v0.1.5. Early, and versioned like it. The wire protocol and the config file are both versioned with forward migration, so an upgrade is a non-event.
  • One machine. The budget covers the host it runs on. A shared broker across machines is designed and seamed for, and deliberately not built — CPU does not aggregate across hosts.
  • Measured on one laptop. An M1 MacBook Air, mostly against Go and Python workloads. calibrate re-derives the constants on yours, but the shape of the model carries that machine's fingerprints and the documents say where.
  • The classifier is imperfect and knows it. It catches 53% of expensive commands by name and gates 36% of cheap ones unnecessarily. It captures 78.6% of the child CPU that matters, which is the figure it is tuned against.

One budget,
behind all of them

If you run more than one Claude Code session on a laptop, the contention is already happening. You are absorbing it instead of scheduling it.

$ curl -fsSL https://raw.githubusercontent.com/peter3605/claude-governor/main/install.sh | sh

Then governor doctor to see what it did, and governor uninstall if you disagree.
